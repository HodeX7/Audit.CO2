Flip the Switch · Track 01 · Team-lead view

Carbon Room Architecture

A Switch chat room where a team closes a month of emissions. Agents collect bills, build one shared ledger and calculate. A rules-based Watchdog posts each missing, conflicting or stale item as a thread with a named owner. Humans fix it in that thread. Only VERIFIED rows count, and a human publishes.

Direct Python client

Mattermost via Switch
Source of truth
SQLite ledger + graph
Freeze
Fri 6 Nov, 17:00 PT

Sat 7 Nov, 10:29 PT
Thin agents, thick ledger.

Every agent is a small piece of glue around one shared core. An LLM is used in exactly two places: extraction (bill text to a structured row) and phrasing (answering a person in plain words from ledger data). Every number and every status change comes from deterministic code. That keeps the demo repeatable and the Watchdog general, and it makes "the model reasons, code calculates, humans publish" true in the code.

trace(tag) -> SourceTag                     # S-### to file, page, excerpt, SHA, factor, recompute
verify_audit(close_id) -> AuditCheck
The rule that makes Switch load-bearing in code

Every human action (resolve, any approval, publish) requires a chat_message_id and an actor that came from a Switch event. The CLI can ingest, calculate and check, so it can produce an unverified draft. It cannot verify a human-gated claim or publish. Without the room, there is no close.

Claim lifecycle

Five statuses: VERIFIED UNVERIFIED CONFLICTING STALE MISSING. Only VERIFIED enters the total. MISSING is an expected source with no row yet, and a false "done" ends there.

stateDiagram-v2
    [*] --> UNVERIFIED: ingest
    UNVERIFIED --> VERIFIED: rules pass and auto tier, or human approves
    UNVERIFIED --> CONFLICTING: R2 conflict
    UNVERIFIED --> STALE: R3 stale factor
    CONFLICTING --> VERIFIED: human picks this one
    CONFLICTING --> Superseded: human picks the other
    STALE --> UNVERIFIED: recalculated with locked factor
    MISSING --> UNVERIFIED: human supplies the source
    VERIFIED --> Superseded: only by a new close version

Close phases

Stored on the close row in the ledger. LangGraph state is only a cache, so after a crash @carbon-room resume rebuilds from the ledger.

07 · What Switch gives us, and what we must prove today

Switch integration and spikes

From the docs: each agent is registered with its own key and gets a WebSocket of message, command and room_join events. Message events carry message_id, thread_id, sender, attachments and addressed. Agents act through HTTP ops such as post_message, send_targeted_message, read_context and the room-document ops. There is no client library, so we implement the protocol ourselves.

Room-client rule: never block the socket

Switch pings every 2 seconds and evicts a connection that is silent for 6. Events go onto a queue, and workers run core and LLM calls in a thread pool. One slow extraction on the socket loop drops the agent mid-demo.

11 · What is most likely to break

Risks

  1. Heartbeat eviction. An LLM call on the socket loop misses a pong and the agent drops out mid-demo. Fix: queue and worker pool.
  2. Threads, attachments and multiple accounts are unproven (S1–S3). Each has a fallback; decide by Wednesday evening, not Thursday.
  3. Extraction varies run to run. Fix: replay cache keyed by SHA, plus the verbatim-excerpt check.
  4. Hard-coded traps or totals. Fix: general rules, test_generalised.py, and totals always computed from VERIFIED rows.
  5. Clean-machine setup. Switch Console and Docker download several GB on first start. Fix: README lists versions and the download, and M5 is scheduled before the freeze.
